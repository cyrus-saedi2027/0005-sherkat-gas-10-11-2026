# Gazyar — Architecture & Engineering Contract

This is the binding contract for everyone writing code in this repo (humans and
agents). Read it fully before touching code. `ROADMAP.md` (Persian) holds the
requirement list (R01…R47) and stage plan; this file holds *how* we build.

---

## 0. Non-negotiables

1. **No business logic in view components.** Screens render; rules live in the
   backend services and in `packages/core`. This is what lets the user app be
   rebuilt as React Native later without touching rules (see §2).
2. **Every number from the business document is a setting**, never a literal
   in code (threshold 3500, points table, co-pay 30/70, free cap, point→rial
   rate, caps, upload limits, OTP limits). Defaults live in the settings
   registry (§4.6).
3. **Every staff mutation is audited** (`audit.record(...)`), every login
   attempt is logged.
4. **No enumeration.** Public auth endpoints never reveal whether a mobile or
   subscription number exists (R09).
5. **Idempotent rewards.** Every points award carries an idempotency key; the
   same event can never pay twice (R13, R24).
6. **Least privilege.** Every admin endpoint declares a permission;
   operators cannot edit finance settings or delete data (R34).
7. **Persian-first UI.** `dir="rtl"`, Persian digits on output, normalised
   digits on input, Jalali dates, no `letter-spacing` on Persian text.
8. **Tests are part of the feature.** A module is not done until its unit,
   API, permission and E2E tests pass on SQLite *and* PostgreSQL, and the full
   suite (all earlier modules) still passes.

## 2. Native-or-web: how the decision is deferred

* Backend is client-agnostic REST + OpenAPI. Auth works for browsers
  (httpOnly refresh cookie) **and** native clients (refresh token in body when
  the request carries `X-Client: native`).
* `packages/core`, `packages/motion`, `packages/data` contain no DOM code, so a
  future `apps/mobile` (Expo / React Native) imports them unchanged.
* `apps/user` is a PWA. `apps/user/capacitor.config.ts` exists so an Android
  APK / iOS build can be produced from the same code (`npx cap add android`).
* Lint rule (enforced by a test in `packages/core`): core/motion/data must not
  import `react-dom`, reference `window`, `document`, or `localStorage`
  directly. Platform services (storage, haptics, camera, device id) are
  injected through `packages/core/src/platform.ts` adapters.

## 3. Domain model

All tables have `id` (int autoincrement unless noted), `created_at`,
`updated_at` (UTC, tz-aware). Money is **integer rials**. Points are
**integers**. Consumption is `float` m³. Jalali periods are strings
`"YYYY-MM"` (e.g. `"1405-07"`), computed in `Asia/Tehran`.

### 3.2 Reference data
| table | key fields |
|---|---|
| `regions` | name, code (unique), parent_id (region → zone hierarchy), is_active |
| `subscribers` (authorised list) | subscription_no (unique, normalised ASCII digits), mobile_enc, mobile_bidx (index), full_name, address, region_id, meter_serial, is_active, import_batch_id, baseline_annual_m3 (cached) |
| `consumption_history` | subscriber_id, jyear, jmonth (1–12), volume_m3, import_batch_id — unique(subscriber_id, jyear, jmonth) |

Baseline (R04): for a target period `(y, m)`, baseline = mean of
`volume_m3` for month `m` over years `y-3 … y-1` that exist. Annual baseline =
mean over those years of the yearly sum. Threshold comparison basis is the
setting `eligibility.threshold_basis` ∈ {`annual`, `monthly_avg`, `period`}.

### 3.3 Files
`files`: uuid hex pk, owner_type, owner_id, purpose (`meter_photo`,
`case_before`, `case_after`, `ticket_attachment`, `content_cover`,
`reward_image`, `import_xlsx`), mime, size, sha256 (index), width, height,
exif_taken_at, storage_key, thumb_key. Images are re-encoded (EXIF stripped
after reading `DateTimeOriginal`), thumbnails generated. Served only through
signed URLs `/api/v1/files/{id}?exp=…&sig=…` (HMAC, short TTL) issued by
endpoints that already checked access.

### 3.4 Readings (stage 1, anomaly rules stage 2)
`meter_readings`: user_id, subscriber_id, period_key, revision (1..n),
kind (`initial`/`correction`/`review_request`), parent_id, is_current (bool;
exactly one current per subscriber+period), input_method (`photo`/`manual`),
declared_value (meter index m³), reading_date (date), photo_file_id,
user_note, status, approved_value, consumption_m3, baseline_m3,
reduction_pct, flags JSON (anomaly codes), reviewer_id, reviewed_at,
reason_code, review_note.

Status machine:
```
pending ──approve──▶ approved
   │  └─flag (auto)─▶ flagged ──approve/needs_correction/reject──▶ …
   ├─needs_correction──▶ needs_correction ──user resubmits──▶ (new revision, kind=correction, pending)
   └─reject──────────▶ rejected
approved / rejected ──user resubmits──▶ (new revision, kind=review_request, pending)
```
Points for a period are keyed `valid_reading:{subscriber_id}:{period_key}` so
revisions never pay twice. `reading_events` keeps the per-reading history
(action, from/to status, old/new value, reason, actor).

Anomaly codes (stage 2, thresholds are settings): `meter_rollback`
(index lower than previous approved), `sudden_drop` (consumption below X% of
baseline), `zero_consumption`, `spike`, `duplicate_photo` (same sha256 seen
for another reading), `exif_mismatch` (photo taken far from reading_date),
`future_date`, `stale_date`.

### 3.5 Cases — technical evaluation & ambassador workflow (stage 2)
`cases`: user_id, subscriber_id, region_id, status, tier
(`no_cost`/`low_cost`/`high_cost`), suggested_tier, needs_field_visit,
ambassador_id, technician_id, assignment_method (`auto`/`manual`),
assigned_at, opened_reason (`first_approved_reading`/`anomaly`/`manual`),
priority, completed_at.

```
new → assigned → contacted → evaluated ─┬─(no visit)──────────────▶ pending_final_approval
                                        └─ visit_scheduled → visited ─┬─(share>0) awaiting_consent ─▶ consent_given → in_execution ─▶ pending_final_approval
                                                                      └─(share=0) in_execution ──────────────────────────────────▶ pending_final_approval
pending_final_approval ─technician approve─▶ completed     (any) ─▶ cancelled / closed_no_action
awaiting_consent ─user declines─▶ consent_declined (→ closed_no_action or re-estimate)
```
Child tables: `case_calls` (called_at, outcome `reached`/`no_answer`/
`wrong_number`/`callback`, note, next_call_at), `case_checklists`
(floor_area_m2, built_area_m2, residents_count, heating_equipment JSON
[{type, count, condition, age_years}], insulation, window_seals,
chimney_status, building_type, notes), `case_visits` (scheduled_start/end,
status), `case_photos` (file_id, phase `before`/`after`, caption),
`case_estimates` (items JSON, total_cost_rial, free_cap_rial snapshot,
subscriber_share_pct snapshot, subscriber_share_rial, program_share_rial,
status `draft`/`sent`/`accepted`/`declined`), `case_events`.

Smart assignment (R38): active ambassadors whose `service_region_ids`
contain the case region (or its parent); pick min(open cases + visits in the
next 7 days); tie → least recently assigned; none → any ambassador; none at
all → stays `new` (unassigned queue).

Cost split: `no_cost`/`low_cost`: program covers up to `finance.free_cap_rial`,
remainder is the subscriber's share. `high_cost`: subscriber pays
`finance.copay_subscriber_pct` (default 30). Any subscriber share > 0
requires consent in the user app before execution (R19).

### 3.6 Points (ledger in stage 1, engine in stage 2, wallet in stage 3)
`points_rules`: event_type (pk), title_fa, points, is_active,
monthly_cap_points (nullable), per_unit (bool). Seeded with R23 values:
`signup` 100, `profile_completed` 20, `valid_reading` 30,
`consumption_reduction` 10 per percent (cap from settings),
`ambassador_cooperation` 50, `referral_success` 100, `survey_completed` 10,
`optimization_executed` 50.

`points_ledger`: user_id, event_type, amount (signed), status
(`pending`/`available`/`suspended`/`reversed`), reason (fa), ref_type,
ref_id, idempotency_key (**unique**), period_key, available_at,
created_by_staff_id, suspended_reason, suspended_by.
* Awards are created `pending` with `available_at` = first instant of the
  next Jalali month (Asia/Tehran) — "usable at the end of each month" (R20).
* `release_due_points(now)` flips due `pending` → `available` (idempotent,
  scheduled daily + CLI).
* Redemptions write negative `available` entries; refunds write positive ones.
* Balances: available / pending / suspended sums.

### 3.7 Referrals (stage 2)
`referrals`: referrer_user_id, referee_user_id (unique), code_used, status
(`pending`/`rewarded`/`capped`/`suspicious`/`rejected`), qualified_at,
reason, signals JSON. Qualification = referee OTP-verified + in authorised
list (both true by construction) + **first approved reading** (R24).
Monthly cap per referrer (`fraud.referral_monthly_cap`). Signals: shared
device_id, device used by > N accounts, same mobile family pattern, etc.
Suspicious referrals wait for finance review.

### 3.8 Content & notifications
`content_articles` (slug, title, summary, body markdown, cover_file_id,
category, target_tiers JSON (empty = all), status, published_at, author_id).
`notifications` (recipient_type, recipient_id, kind, title, body, data JSON,
read_at). `sms_outbox` (mobile_enc, text, purpose, status, provider_ref,
error, attempts, sent_at) — SMS is queued and sent by a background worker so
response timing never depends on the SMS provider. `broadcasts` (stage 3).

### 3.9 Store, finance (stage 3)
`reward_categories` (key, title, icon, sort), `reward_items` (category_id,
title, description, image_file_id, kind `product`/`discount`/`cash`/
`donation`, points_cost, rial_value, stock nullable, is_active,
charity_name), `redemptions` (user_id, item_id?, kind, points, rial_value,
status `submitted`/`approved`/`rejected`/`fulfilled`/`cancelled`,

### 3.10 Tickets (stage 3)
`tickets` (tracking_code unique `GZ-YYMMDD-NNNNN`, user_id, subject_key,
title, status `open`/`in_progress`/`awaiting_customer`/`answered`/
`resolved`/`closed`, priority `low`/`normal`/`high`/`urgent`, assigned_unit

### 4.1 Error contract
```json
{"error": {"code": "not_eligible", "message": "اطلاعات واردشده برای این طرح قابل تأیید نیست؛ لطفاً با پشتیبانی تماس بگیرید.", "details": {}}}
```
Codes are stable snake_case strings; clients switch on `code`, display `message`.

### 4.2 Auth flows
Subscriber (app):
1. `POST /api/v1/app/auth/signup/start {mobile, subscription_no, referral_code?, device_id}` → normalise → rate-limit (per IP, per mobile) → eligible iff subscriber row matches (subscription_no, mobile_bidx), is active, baseline ≥ threshold. Eligible → OTP challenge queued (also when an account already exists — verify then logs in). Not eligible → 422 `not_eligible` with the exact R09 text. Same work on both paths; SMS is queued, never sent inline.
2. `POST /signup/verify {challenge_id, code}` → `{signup_token}` or, if the account exists, tokens.
3. `POST /signup/complete {signup_token, accept_terms, accept_privacy, login_method, password?, first_name?, last_name?, device_id}` → user + `signup` points (idempotent) + referral row → tokens.
4. Login: `/login/otp/start {mobile}` (always answers `otp_sent`; only sends if user exists), `/login/otp/verify`, `/login/password` (lockout after N failures).

Staff (admin): `POST /api/v1/admin/auth/login {username, password}` → tokens, or `{otp_required, challenge_id}` when 2FA is on → `/admin/auth/login/verify`.

Common: `POST /api/v1/auth/refresh`, `POST /api/v1/auth/logout`. Web: refresh
token in httpOnly `SameSite=Strict` cookie scoped to `/api/v1/auth`; native:
body when `X-Client: native`.

### 4.4 Security (R34–R36, R42)
* Body limit 1 MB JSON, uploads ≤ `uploads.max_mb` (default 8), image pixels
  ≤ 40 MP; allowed types jpeg/png/webp/heic.
* Rate limits (settings): OTP send per mobile 3/10 min & 10/day, per IP
  20/10 min; OTP verify attempts 5 per challenge; staff login 5 fails →
  15 min lock; API per subject 120/min; uploads 30/day/user.
* OTP: 5 digits, 120 s TTL, hashed (HMAC), single use, resend cooldown 60 s.
* Headers: `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options:
  DENY`, `Strict-Transport-Security` (prod), restrictive CSP on API.
* Sensitive fields encrypted (mobile, national code, IBAN); searchable via
  blind index; masked in list responses (`0912***4567`).
* Every list endpoint paginates (max 100).

## 5. Backend module conventions

```
app/modules/<name>/
  models.py        SQLAlchemy models (import Base from app.core.db)
  schemas.py       Pydantic v2 in/out models (no ORM objects leak out)
  service.py       business logic; pure functions taking (db, …); raises AppError
  router_app.py    subscriber-facing routes  → mounted at /api/v1/app/<name>
  router_admin.py  staff routes              → mounted at /api/v1/admin/<name>
```
* Routers are thin: parse → permission → call service → return schema.
* Cross-module calls go through the other module's `service.py` public
  functions only (never its models directly from routers).
* Every admin route: `dependencies=[Depends(require(Permission.X))]`.
* Every staff mutation: `audit.record(...)` inside the same transaction.
* Points are only ever written by `app.modules.points.service.award(...)` /
  `.spend(...)` / `.refund(...)` / `.suspend(...)`.
* Notifications only through `app.modules.notifications.service.notify(...)`.

Module list (registry in `app/api.py`): `auth`, `staff`, `audit`,
`settings`, `files`, `regions`, `subscribers`, `users`, `readings`,
`notifications`, `points`, `dashboard` (stage 1); `cases`, `referrals`,
`content`, `analytics` (stage 2); `store`, `finance`, `tickets`, `reports`,
`surveys` (stage 3).

## 6. Frontend conventions

### 6.1 Design system (`packages/ui`) — adapted from MediStock
* Motion: `packages/motion` (`Spring`, shared ticker, presets with damping
  ratios reasoned in comments, reduced-motion handled in the engine).
  `packages/ui/motion` adds React bindings (`useSpringRef`, `useSpringBind`
  hot path writing to the DOM — zero re-renders; `useSpringState` cold path).
* Tokens: radii named by what they wrap (`R.card`), shadows by placement,
  `GESTURE` thresholds table, `Z` scale. Theme = typed palette → CSS custom
  properties (`v("ink")`), switching costs zero React renders; light + dark.
* Styling: CSS Modules + CSS variables (cascade, `:hover`, `:focus-visible`,
  media queries for the responsive admin). Inline styles only for values
  written by springs.
* Text: `Title/Head/Body/Cap`, `<Num>` (Persian digits, `٬` grouping, `bdi`),
  `<Lat>` for Latin runs, **no letter-spacing on Persian**, line-height 1.45–1.75.
* Font: Vazirmatn self-hosted (woff2, 400/500/700/800), `font-display: swap`.
* Components: Pressable (window pointerup), Button, Field, Select, Switch,
  Segmented, Chip, Card, Row, Stat, Ring, Empty, Skeleton, Toast, Sheet
  (draggable, interruptible), Dialog, overlay stack (back closes top
  overlay), VirtualList, JalaliDatePicker, Charts (Line/Bar/Donut/Sparkline,
  animated draw-in, accessible), Icons (hand-drawn 24px grid).
* Motion inventory (must exist and feel coherent): screen push/pop with
  parallax + interactive swipe-back, nav pill on the `cradle` spring,
  draggable sheets, staggered list reveal, count-up numbers, chart draw-in,
  success check/confetti for rewards, shake on error, skeleton shimmer,
  pull-to-refresh, toast slide, progress ring for uploads, shared-element
  photo zoom. All honour `prefers-reduced-motion`.

### 6.2 Apps
* `apps/user`: phone-first PWA, stack router with swipe-back + tab bar (pill
  nav), deep links via History API, offline banner, installable manifest,
  service worker (cache-first assets, network-first API), Capacitor config.
* `apps/admin`: responsive (≥1280 desktop, tablet, phone usable), React
  Router 7, sidebar filtered by permissions, keyboard-friendly review queue,
  data tables with server pagination/sorting/filtering, Jalali range filters.
* Server state: TanStack Query hooks in `packages/data`. Mutations invalidate
  precise keys. Errors → toast with server `message`.
* Feature folders: `apps/<app>/src/features/<feature>/` with `index.tsx`
  exporting route elements; route tables in `apps/<app>/src/routes.tsx`.

### 6.3 Frontend tests
* Vitest for `packages/*` (pure logic, spring maths, validators, digits,
  jalali, normalise fixtures shared with backend).
* Component tests (Vitest + Testing Library, jsdom) for interactive kit
  pieces.
* Playwright E2E (`e2e/`) on a seeded backend: mobile viewport (390×844) for
  the user app, 1440×900 + 768×1024 for admin; screenshots kept as artifacts.
